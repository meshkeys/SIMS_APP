# 3. Data model

The full model lives in `apps/server/prisma/schema.prisma` (about 40 tables). This chapter
explains its structure and conventions.

## 3.1 Model groups

| Group | Tables | Notes |
|---|---|---|
| Tenancy & identity | Organisation, Subscription, User, Membership, Invitation, Department, DeviceToken, RefreshToken | A **User** is global (one login); a **Membership** is that user inside one organisation, with roles. Owners/sponsors always point at Membership, never User |
| Strategy framework | StrategicPlan, FrameworkLevel, StrategyElement, CustomFieldDefinition | No "Pillar" table: levels and elements are data |
| Measurement (impact) | Kpi, KpiTarget, KpiActual | Interim targets are typed rows, not JSON |
| Delivery (execution) | Initiative, InitiativeObjectiveLink, InitiativeKpiLink, Milestone, Task, Dependency, ProgressSnapshot | An initiative can contribute to several objectives with weights |
| Risk & governance | RiskIssue, Escalation, EscalationLevelChange, Decision, Approval, Ruleset | Escalations come from risks, missed updates, missing KPI actuals, dependencies, resource conflicts |
| Reporting cycle | ReportingPeriod, StatusUpdate, StatusUpdateLine, Comment, ReportSnapshot, ReportPack | Per-milestone claimed vs verified figures; challenge threads |
| Benefits | Benefit, BenefitProfile, BenefitActual | Expected/forecast per period and realised actuals |
| Platform | Document, Notification, AuditEvent | Audit is append-only |

## 3.2 Configurable strategy hierarchy

```
StrategicPlan ── FrameworkLevel (depth 1..n, label, plural label, code prefix, allowsKpis)
                      │
                 StrategyElement (level, parent) ── tree of any shape
                      │                 │
                     Kpi        InitiativeObjectiveLink (contributionWeight, isPrimary)
                                         │
                                    Initiative ── Milestone ── Task
```

- An organisation chooses a template (Strategic pillars, Balanced Scorecard, OKRs, Public
  sector results, or custom) and then renames, adds or removes levels (1–10).
- Any number of elements per level, KPIs per element, initiatives per element.
- Display names for fixed record types come from `Organisation.terminology`
  (e.g. "Initiative" → "Project", "KPI" → "Outcome indicator").

## 3.3 Completion and health

- **Completion %** = Σ(milestone weight × verified completion) ÷ Σ weight.
- **Planned %** at a date comes from each milestone's planned window
  (`baselineStartDate` → `baselineDate`).
- **Calculated health** comes from the active ruleset (chapter 7); the reasons are stored in
  `Initiative.healthReasons` so the UI can show "Why this status?".
- **Override** (`healthOverride`) requires a reason, author and expiry — enforced by a
  database CHECK constraint, not just the API.

## 3.4 Conventions

| Convention | Rule |
|---|---|
| Identifiers | UUIDv7 (time-ordered), generated by the application |
| Tenant column | Every tenant-owned table has `organisationId`. The name is reserved for this meaning |
| Tenant-safe relations | Parent → child relations use composite keys `[parentId, organisationId] → [id, organisationId]`, so a row can never reference another tenant's parent |
| Deletion | Deleting an Organisation cascades to all its data in one statement. Required relations use `NO ACTION`, so deleting e.g. a period that still has updates is refused |
| Money | `Decimal(20,2)` in the organisation's currency |
| Percentages | `Decimal(5,2)` constrained 0–100 |
| Dates vs instants | Calendar dates are `@db.Date`; moments are timestamps (UTC) |
| History | Never update in place what must be auditable: use snapshots, change rows and AuditEvent |
| JSON columns | Only for genuinely flexible data (ruleset config, custom field values, snapshots). Validated by zod in the API |

## 3.5 Database-level integrity rules

About 40 CHECK constraints protect the data even from bugs, for example: progress and
weights between 0 and 100; end dates not before start dates; escalation level 1–10; risk
likelihood and impact 1–5; a dependency cannot point at itself; an override must be
complete; lower-case emails; valid workspace slugs. A partial unique index ensures only
**one ACTIVE ruleset per organisation**.

## 3.6 Migrations (to date)

| Migration | Purpose |
|---|---|
| `…_init` | All tables, enums, indexes, composite tenant keys |
| `…_rls_constraints_and_grants` | Row-level security on every tenant table; append-only audit; CHECK constraints; one active ruleset |
| `…_configurable_escalation_ladder` | Ladder of 1–10 levels; level names recorded in history |
| `…_allow_tenant_cascade_delete` | NO ACTION on required relations so a tenant can be deleted cleanly |
| `…_auth_membership_lookup` | `sims_auth_memberships()` — the sign-in lookup (chapter 4) |
| `…_refresh_token_not_tenant_scoped` | RefreshToken is user data: column renamed, RLS removed |
| `…_invitation_token_lookup` | `sims_invitation_by_token_hash()` for the accept page; index for invitation lists |
