# 11. Architecture decision records

Each record states the context, the decision and its consequences. Records are never
edited after acceptance; a later decision supersedes an earlier one by number.

---

## ADR-001 — Monorepo with npm workspaces

**Status:** Accepted · 2026-10-17

**Context.** The API and web app share types and validation rules, and change together.

**Decision.** One repository: `apps/server`, `apps/client`, `packages/*`, managed by npm
workspaces from the root.

**Consequences.** One install and one place for CI; shared contracts can't drift. Tooling
must be workspace-aware (scripts run from the root).

---

## ADR-002 — PostgreSQL with row-level security for tenant isolation

**Status:** Accepted · 2026-10-17

**Context.** SIMS is multi-tenant SaaS holding confidential strategy data. A single missing
`where organisationId = …` in application code must not leak data.

**Decision.** Shared database, shared schema, `organisationId` on every tenant table, and
PostgreSQL RLS policies keyed on a per-transaction setting. The API connects as a role
that cannot bypass RLS.

**Consequences.** Isolation holds even with application bugs. Every operation runs in a
short transaction (small overhead). Cross-tenant work (sign-in) needs explicit, narrow
`SECURITY DEFINER` functions. Migrations must enable RLS on new tables (enforced by test).

---

## ADR-003 — Composite tenant foreign keys

**Status:** Accepted · 2026-10-17

**Context.** RLS checks each row, not the relationship between rows: a row could still
point at another tenant's parent.

**Decision.** Parent → child relations reference `[id, organisationId]`.

**Consequences.** The database rejects cross-tenant references outright. Slightly larger
indexes; Prisma relations list two fields.

---

## ADR-004 — UUIDv7 identifiers

**Status:** Accepted · 2026-10-17

**Context.** Random UUIDv4 keys fragment B-tree indexes at high insert volumes; sequential
integers leak volume and complicate bulk inserts.

**Decision.** Time-ordered UUIDv7, generated by the application.

**Consequences.** Compact, append-friendly indexes; ids are known before insert (needed
to set the tenant context when creating an organisation).

## ADR-005 — Configurable strategy hierarchy

**Status:** Accepted · 2026-10-17

**Context.** Organisations structure strategy differently (pillars, Balanced Scorecard,
OKRs, public-sector results) and with different numbers of items.

**Decision.** No fixed "Pillar"/"Objective" tables. `FrameworkLevel` defines levels per
plan; `StrategyElement` is a tree node at a level. Display names come from organisation
settings.

**Consequences.** Any framework of 1–10 levels is supported without schema changes. The UI
must never hard-code level names or counts.

---

## ADR-006 — Governance rules as versioned, validated JSON

**Status:** Accepted · 2026-10-17

**Context.** RAG thresholds, health modifiers, override policy, the escalation ladder and
the reporting cycle differ by organisation and change over time under maker-checker.

**Decision.** One `Ruleset.config` JSON document per version, validated by a zod schema
with a `schemaVersion`; one `ACTIVE` version per organisation (partial unique index).

**Consequences.** Rules change without migrations, with full history. The shape must be
versioned deliberately; validation lives in one place shared with the admin UI.

---

## ADR-007 — Configurable escalation ladder (1–10 levels)

**Status:** Accepted · 2026-10-17 (supersedes the fixed 4-level ladder in the original schema)

**Context.** Small organisations want two levels; large groups need five or more.

**Decision.** Levels, names, deciders and timings live in the ruleset. The database only
checks a 1–10 range. Level history stores the level name at the time.

**Consequences.** Any ladder shape works; history remains readable after ladder edits.

---

## ADR-008 — Tenant deletion by cascade with NO ACTION on required relations

**Status:** Accepted · 2026-10-17

**Context.** Offboarding a customer must remove all their data reliably; default
`RESTRICT` foreign keys blocked a cascading delete.

**Decision.** Required relations use `NO ACTION` (checked at statement end).

**Consequences.** `DELETE FROM "Organisation"` removes a tenant in one statement; deleting
an in-use record on its own is still refused.

## ADR-009 — Session design: short JWT access tokens + rotating opaque refresh tokens

**Status:** Accepted · 2026-10-18

**Context.** Authentication must be cheap at scale, resistant to token theft, and must let
role changes and deactivations take effect quickly.

**Decision.** 15-minute HS256 JWT access tokens held in memory; 30-day opaque refresh tokens
stored as hashes, rotated on every use with family-wide revocation on replay, delivered in
an `httpOnly`, `SameSite=Strict` cookie scoped to the auth endpoints; Argon2id passwords.

**Consequences.** No database call to authenticate API requests; XSS cannot read the
long-lived credential; permission changes lag by at most 15 minutes. Mobile clients will
need a non-cookie refresh path (planned).

## ADR-010 — `organisationId` means tenant-owned

**Status:** Accepted · 2026-10-18

**Context.** RefreshToken had an `organisationId` column (the workspace a session uses), so
the schema-wide RLS rule treated user data as tenant data and blocked it.

**Decision.** The column name `organisationId` is reserved for tenant-owned, RLS-protected
data. RefreshToken uses `activeOrganisationId` and has no RLS.

**Consequences.** One simple, testable rule: every table with `organisationId` has RLS.

## ADR-011 — RFC 9457 Problem Details for errors

**Status:** Accepted · 2026-10-18

**Context.** Clients need one predictable error shape, with machine-readable codes and
field-level validation messages.

**Decision.** All errors are `application/problem+json` with a stable `code`, optional
`errors[]`, and the `requestId`.

**Consequences.** Clients branch on `code`; support can trace any error by `requestId`.

---

## ADR-012 — Email through a `Mailer` port; send after commit

**Status:** Accepted · 2026-10-18

**Context.** Invitations (and later notifications) send email. Email providers fail and
are slow; tests must not send real mail; the provider may change.

**Decision.** Feature code depends on a `Mailer` interface. The SMTP implementation works
with any provider (Mailpit locally). Mail is sent only after the database transaction
commits; a failure is logged and reported to the caller (`emailDelivered: false`) and the
record can be resent.

**Consequences.** A mail outage never loses data or rolls back business actions. Tests
swap in a fake mailer and read the emailed link. Delivery is not retried automatically
until the jobs module adds a queue.

## ADR-013 — One read model per screen; flat element lists

**Status:** Accepted · 2026-10-18

**Context.** Screens like the Strategy map combine plan, levels, elements, people, KPIs
and initiative health. Assembling that from many generic endpoints means many round trips
and N+1 queries as plans grow.

**Decision.** Each data-heavy screen gets a read endpoint shaped for it (e.g.
`GET /plans/:id/map`) that runs a fixed number of queries and returns stored rollups.
Trees are returned as flat lists with `parentId`; the client builds the hierarchy.
Generic CRUD endpoints remain for editing.

**Consequences.** Fast screens with predictable database load at any plan size; one place
to cache later. Read models must be updated when screens change.

## ADR-014 — Validate membership references explicitly

**Status:** Accepted · 2026-10-18

**Context.** Foreign keys are checked by PostgreSQL without row-level security, and
person references (owner, sponsor) are plain foreign keys, so another tenant's membership
id would pass the database check.

**Decision.** Every write that sets a membership reference calls `assertActiveMembers`,
which reads through row-level security and requires an active member.

**Consequences.** Cross-tenant references are impossible through the API; one helper to
reuse in every module (initiatives, risks, tasks…).

## ADR-015 — Health is a pure function of facts and rules

**Status:** Accepted · 2026-10-18

**Context.** Initiative health drives the dashboard, escalations and Board packs. It must
be explainable, configurable per organisation, and identical wherever it is computed.

**Decision.** Completion and health live in `src/domain/delivery` as pure functions:
facts + ruleset in, status + reasons out. No database or framework access. The order is
fixed: progress band → Amber caps → forced Red → Unknown for a missed update in the last
locked period. Reasons are stored with the status.

**Consequences.** Exhaustively unit-tested; the same code serves requests, jobs, the seed
(which now proves the engine reproduces every wireframe status) and the rules "impact
preview". Changing the order of rules is a deliberate, versioned decision.

## ADR-016 — Missing updates: flag when overdue, Unknown when locked

**Status:** Accepted · 2026-10-18 (refines the missed-update rule in ADR-015)

**Context.** A status built on old figures misleads. But turning an initiative "Unknown"
as soon as a cycle opens, or the minute a deadline passes, punishes owners who still have
time and floods dashboards with Unknowns.

**Decision.** Two stages. After the open period's submission deadline passes with no
update, the status is kept and flagged "Update overdue · N days" (a `FLAG` reason; no
status change). When the period locks without an update, the status becomes Unknown —
unless an overdue critical milestone forces Red.

**Consequences.** Live screens stay truthful and actionable (people see exactly what is
late); Board packs never carry unverifiable figures. Because planned progress keeps
rising, an initiative that goes silent drifts worse on its own. The flag depends on the
clock, so health must be recalculated at least daily (delivery slice).

## ADR-017 — An injectable clock for business time

**Status:** Accepted · 2026-10-18

**Context.** Planned progress, overdue milestones, overdue updates and override expiry all
depend on "now". Code that calls `new Date()` directly cannot be tested at a chosen moment,
and results would drift as real time passes.

**Decision.** Business logic asks a `Clock` (injected with the `CLOCK` token). Production
binds the system clock; tests bind a `FixedClock` they can move.

**Consequences.** Deterministic tests at any date (the suite runs at the wireframes' moment
and moves forward to test expiry and drift). One rule for reviewers: no `new Date()` for
"now" in business logic.

## ADR-018 — Page-numbered pagination for registers

**Status:** Accepted · 2026-10-18

**Context.** The Initiative register shows "Page 1 of 4" with jumps between pages, sorted by
computed effective health. Cursor pagination cannot jump to page N and is awkward with
computed sort keys.

**Decision.** Registers of bounded size per tenant (initiatives, risks, KPIs) use
page/pageSize with totals, computed in one indexed SQL statement. Unbounded streams
(activity, audit, notifications) will use cursors.

**Consequences.** Matches the screen's interaction; deep offsets are cheap at tenant scale.
Revisit if a single tenant's register grows past tens of thousands of rows.

## ADR-019 — Per-initiative permissions and a baseline that locks at activation

**Status:** Accepted · 2026-10-18

**Context.** Role checks alone are too coarse: an Executive Sponsor must not edit an
initiative someone else sponsors, and once delivery starts the agreed plan is what progress
and health are measured against, so it cannot drift silently.

**Decision.** Writes are authorised by the caller's relation to the initiative (Strategy
Office, its sponsor, its owner) and by field group (accountability, shape, narrative,
baseline). When an initiative becomes active its baseline — dates, budget and the milestone
plan (weights, baseline dates, critical flags, adding/removing) — locks for everyone but
the Strategy Office; forecasts, narrative, tasks and dependencies stay open. Every change
re-runs the health rules in the same transaction.

**Consequences.** Owners keep day-to-day control without being able to move the goalposts.
Baseline changes become rare, visible events (`BASELINE_CHANGED`) — and, with the
governance slice, will go through maker-checker change requests instead of direct edits.

## ADR-020 — Verified figures drive everything; locked periods are frozen

**Status:** Accepted · 2026-10-18

**Context.** Owners are optimistic about their own progress; reports must not drift after
management has approved them; deadlines must mean the same thing in every organisation's
time zone.

**Decision.** Owners *claim* completion per milestone; only the Strategy Office *verifies*,
never above the claim, and only verified figures become milestone completion (and so
progress and health). Cycle deadlines are computed once, in working days at 17:00 local time,
and stored on the period. Locking a period recalculates health, writes progress snapshots and
a report snapshot, and makes the period read-only.

**Consequences.** "Claimed vs verified" is visible at every step and auditable; Board packs
read frozen snapshots, so the numbers never change after approval; rule changes never move a
live cycle. Public holidays are not yet in the working-day calendar.

---

## ADR-021 — Active baselines change only through maker-checker change requests

**Status:** Accepted · 2026-10-18 (supersedes the Strategy Office exception in ADR-019)

**Context.** ADR-019 let the Strategy Office edit a locked baseline directly until change
requests existed. With them in place, any direct edit — even by the Office — would let the
goalposts move without a second pair of eyes.

**Decision.** Once an initiative is active, nobody edits its baseline directly. Changes go
through a change request with a justification, decided by the MD/CEO (baseline) or the
sponsor (budget, scope) — and never by the requester. Approval re-validates the change
against the current baseline before applying it.

**Consequences.** Every change to what was promised has a requester, an approver, a reason
and a before/after record. Urgent fixes need an approver available; the request shows in
their "Decisions required" with a due date.
